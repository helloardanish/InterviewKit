## 1. Problem in Simple Words

**Given:** an initial capital `w`, an integer `k`, and `n` projects, where project `i` needs at least `capital[i]` to start and adds `profits[i]` to your capital when finished.

**Required:** choose **at most `k` distinct projects** (each project at most once) to maximize your final capital, and return that final capital. A project can only be started if your current capital is at least its `capital[i]`; capital is not spent, so finishing a project only adds profit.

**Constraints that matter:**
- `1 <= n <= 10^5` and `1 <= k <= 10^5` — an approach that rescans all projects in each of `k` rounds is about `10^10` operations, too slow. Roughly `O((n + k) log n)` is the target.
- `0 <= profits[i] <= 10^4` — profits are **non-negative**. This is the key constraint: capital never decreases, so any project that is affordable now stays affordable forever, and taking a project never hurts.
- `0 <= capital[i] <= 10^9` and `0 <= w <= 10^9` — large thresholds, but only comparisons against `w` are needed. A project with `capital[i] == w` is affordable (use `<=`).
- "At most `k`" — you may stop early, and you must stop if nothing is affordable. The answer is guaranteed to fit in a 32-bit signed integer (the largest possible total is about `2 * 10^9`), so `int` suffices.

## 2. Recognition Signals

- "Choose at most `k` items to maximize a total" where each choice **unlocks** more options: this is greedy plus a heap of the currently available options.
- Items become available when a monotone resource (here, capital) passes a threshold, and the resource only grows. The set of available items therefore only grows, which suggests **sorting by threshold** and unlocking items with a moving pointer.
- "Pick the best available" at every step means a **max-heap** over the available items.
- Pattern: **sort projects by required capital; each round, move all newly affordable projects into a max-heap of profits and take the largest.**

## 3. Core Idea

Sort the projects by `capital`. Repeat up to `k` times: push the profits of every project whose capital is now at most `w` into a max-heap (advancing a pointer through the sorted list so each project is pushed once), then, if the heap is empty, stop; otherwise take the largest profit and add it to `w`.

**Greedy choice:** at every step, take the affordable unused project with the largest profit.

**Exchange argument:** let `P` be the affordable project with the largest profit, and let `S` be any optimal plan of at most `k` projects. If `S` does not contain `P`, replace its first project (which is affordable now and has profit at most `profit(P)`) with `P`; the capital after this first step is at least as large as before, so every later project of `S` is still affordable, and the total does not decrease. If `S` contains `P` later, move `P` to the front: it is affordable now, and every project that used to precede it is now preceded by extra non-negative profit, so each is still affordable, and the total is unchanged. Either way there is an optimal plan that begins with `P`, and the argument repeats from the new capital.

**Invariant:** at the start of each round, after unlocking, the heap contains exactly the profits of all unused projects with `capital <= w`.

## 4. Approach 1 — Brute Force

In each of up to `k` rounds, scan every project, find the unused affordable one with the largest profit, take it, and mark it used.

```java
public int findMaximizedCapitalBruteForce(int k, int w, int[] profits, int[] capital) {
    int n = profits.length;
    boolean[] used = new boolean[n];

    for (int round = 0; round < k; round++) {
        int best = -1;
        for (int i = 0; i < n; i++) {
            if (!used[i] && capital[i] <= w
                    && (best == -1 || profits[i] > profits[best])) {
                best = i;
            }
        }
        if (best == -1) {
            break;
        }
        used[best] = true;
        w += profits[best];
    }
    return w;
}
```

**Time:** O(k · n), about `10^10` in the worst case.
**Space:** O(n) for the `used` array.

Not optimal: it uses the correct greedy rule but recomputes the affordable set from scratch every round. Since capital only grows, the affordable set only grows, so it can be maintained incrementally.

## 5. Approach 2 — Optimized (Sort by Capital + Max-Heap of Profits)

1. Pair each project's capital and profit and sort the pairs by capital ascending.
2. Keep a pointer `next` into the sorted list and a max-heap of profits.
3. For each round (up to `k`): while `next < n` and `capital <= w`, push that project's profit and advance `next`.
4. If the heap is empty, stop. Otherwise `w += heap.poll()`.
5. Return `w`.

```java
public int findMaximizedCapital(int k, int w, int[] profits, int[] capital) {
    int n = profits.length;
    int[][] projects = new int[n][2];
    for (int i = 0; i < n; i++) {
        projects[i][0] = capital[i];
        projects[i][1] = profits[i];
    }
    Arrays.sort(projects, (a, b) -> Integer.compare(a[0], b[0]));

    PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Collections.reverseOrder());
    int next = 0;

    for (int round = 0; round < k; round++) {
        while (next < n && projects[next][0] <= w) {
            maxHeap.offer(projects[next][1]);
            next++;
        }
        if (maxHeap.isEmpty()) {
            break;
        }
        w += maxHeap.poll();
    }
    return w;
}
```

**Time:** O((n + k) log n). Sorting is O(n log n); each project is pushed at most once and each of at most `k` rounds does one poll, each costing O(log n).
**Space:** O(n) for the sorted pairs and the heap.

This is optimal in the sense that the sort and heap are standard and no step is repeated: the affordable set is maintained incrementally, and no project is examined more than a constant number of times outside heap operations.

## 6. Dry Run

Example 1: `k = 2`, `w = 0`, `profits = [1,2,3]`, `capital = [0,1,1]`. The tricky part is that round 2 takes profit 3, not profit 2, even though both are affordable.

Sorted by capital (capital, profit): `(0,1)`, `(1,2)`, `(1,3)`.

| Round | w at start | Unlocked this round | Heap after unlocking | Polled | w after |
|---|---|---|---|---|---|
| 1 | 0 | (0,1); next project needs 1 > 0, stop | {1} | 1 | 1 |
| 2 | 1 | (1,2), (1,3) | {2, 3} | 3 | 4 |

Exit condition: `k = 2` rounds done. Final answer: `4`.

## 7. Complexity Summary

| Approach | Time | Space | Notes |
|---|---|---|---|
| Rescan all projects each round | O(k · n) | O(n) | About `10^10` operations; too slow |
| Sort by capital + max-heap of profits | O((n + k) log n) | O(n) | Each project pushed once; at most `k` polls |

## 8. Edge Cases

| Case | Why it is tricky | How the code handles it |
|---|---|---|
| No project affordable at the start (all `capital[i] > w`) | Nothing can be taken; polling an empty heap would fail | Heap is empty in round 1, so the loop breaks and `w` is returned unchanged |
| Fewer affordable-over-time projects than `k` | The loop must stop early rather than spin or poll an empty heap | `isEmpty()` check breaks out; `poll()` on an empty queue returns `null`, which would throw on unboxing |
| `capital[i] == w` exactly | Off-by-one on affordability | Condition is `<=`, so such a project is affordable |
| Zero-profit projects | Taking them changes nothing | They are harmless: `w += 0`; the greedy still picks higher profits first |
| Many equal profits | Ties in the heap | Any tied project is equivalent for the total |
| A chain where each project unlocks the next | Needs the incremental unlocking each round | The `while` loop pushes newly affordable projects at the start of every round |
| `k` larger than `n` | Cannot take more than `n` distinct projects | Heap runs empty after all are taken, then the loop breaks |
| Large `w` making everything affordable | All projects go into the heap in round 1 | The pointer loop pushes them all once; later rounds just poll |
| Total near `2 * 10^9` | Integer range | Guaranteed to fit in `int` by the problem; capital and profit additions stay within it |

## 9. Java Notes

- `PriorityQueue<Integer>` is a min-heap by default; `new PriorityQueue<>(Collections.reverseOrder())` makes it a max-heap of profits.
- `PriorityQueue.poll()` returns `null` on an empty queue, so `w += maxHeap.poll()` without an emptiness check would throw `NullPointerException` from unboxing. Always guard with `isEmpty()`.
- Sort with `Integer.compare(a[0], b[0])`, not subtraction. Here the values are non-negative so subtraction would not overflow, but the habit is safer.
- `Arrays.sort` on an `int[][]` with a comparator sorts the row arrays by capital; pairing capital and profit in one row keeps them together.
- The `next` pointer advances monotonically, so each project is pushed into the heap exactly once; the `while` loop's total work across all rounds is O(n), not O(n) per round.
- Since `k` and `n` can both be `10^5`, avoid any per-round rebuild of the heap.

## 10. Common Mistakes

- Always picking the cheapest-capital project instead of the highest-profit affordable one. Fix: among affordable projects, maximize profit.
- Using a min-heap of profits, which takes the smallest profit each round. Fix: use a max-heap.
- Forgetting the `isEmpty()` break, causing a `NullPointerException` (or wasted rounds) when nothing is affordable. Fix: break out when the heap is empty.
- Using `<` instead of `<=` for affordability, which skips projects with `capital == w`. Fix: `capital <= w`.
- Rescanning every project each round to find the affordable ones (the brute force), giving O(k · n). Fix: sort by capital and advance a pointer.
- Pushing a project into the heap more than once, or not removing it after use. Fix: the pointer pushes each project once and `poll()` removes it.
- Assuming exactly `k` projects must be done. The problem allows at most `k`; stopping early is correct when nothing is affordable.

## 11. Interview Takeaway

- **Trigger sentence:** "Repeatedly take the best option among those currently unlocked, where unlocking only grows with capital, means sort by the unlock threshold and keep a max-heap of the unlocked options."
- **90-second explanation:** Capital only ever increases because profits are non-negative, so any project I can afford now stays affordable. That makes greedy safe: at each step I take the affordable project with the largest profit. An exchange argument shows it: any optimal plan can be rearranged to start with that project without lowering the total, since moving a project earlier only adds capital sooner. To make it efficient, I sort projects by required capital and keep a pointer plus a max-heap of profits. Each round I push every project that has become affordable, so each project enters the heap once, then I pop the largest profit and add it to my capital. If the heap is ever empty I stop, since nothing is affordable and the problem says at most `k`. Sorting is O(n log n) and there are at most `k` pops, so it is O((n + k) log n) time and O(n) space, versus O(k · n) if I rescanned every round.
- **Related problems:** 215 (Kth Largest Element in an Array), 295 (Find Median from Data Stream), 373 (Find K Pairs with Smallest Sums), 621 (Task Scheduler).

## 12. Recall Questions

**Q:** Why is the greedy choice (largest affordable profit) safe?
**A:** Profits are non-negative, so capital never decreases. Taking the largest-profit affordable project first can be swapped into any optimal plan without making any later project unaffordable or lowering the total.

**Q:** Why sort by capital and use a pointer instead of rescanning projects each round?
**A:** The set of affordable projects only grows as capital grows, so a pointer through the capital-sorted list unlocks each project exactly once, avoiding repeated scans.

**Q:** Why a max-heap of profits and not capitals?
**A:** Once a project is unlocked, its capital no longer matters; the only question is which unlocked project adds the most capital, which is the largest profit.

**Q:** What happens if the heap is empty in some round?
**A:** No unused project is affordable, and capital cannot increase, so no later round can change that; the loop should stop and return the current capital.

**Q:** Why can the loop stop early without hurting correctness?
**A:** The problem asks for at most `k` projects. If nothing is affordable now, capital stays the same forever, so no further project can ever be taken.

## 13. Final Code

```java
import java.util.*;

class Solution {
    public int findMaximizedCapital(int k, int w, int[] profits, int[] capital) {
        int n = profits.length;
        int[][] projects = new int[n][2];
        for (int i = 0; i < n; i++) {
            projects[i][0] = capital[i];
            projects[i][1] = profits[i];
        }
        Arrays.sort(projects, (a, b) -> Integer.compare(a[0], b[0]));

        PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Collections.reverseOrder());
        int next = 0;

        for (int round = 0; round < k; round++) {
            while (next < n && projects[next][0] <= w) {
                maxHeap.offer(projects[next][1]);
                next++;
            }
            if (maxHeap.isEmpty()) {
                break;
            }
            w += maxHeap.poll();
        }
        return w;
    }
}
```
